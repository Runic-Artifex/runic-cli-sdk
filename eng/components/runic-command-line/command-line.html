Dedicated command-line plan · implementation specification

A small CLI layer for applications that also have a UI.

Evaluate and, only if differentiated requirements remain, build a Native-AOT-safe command layer for hosted applications: explicit command registration, console abstraction, stable exit codes, typed machine responses, safe child-process invocation, and deterministic coexistence with a graphical launch mode. This document is self-contained; implementation must not depend on any private repository or unpublished source.

00 · Charter

Purpose, boundaries and normative vocabulary

The library serves applications that expose both an interactive UI and automation commands. It is a command execution and host-integration layer, not a terminal UI toolkit and not a remote execution service.

Goals

  • One immutable command model for human invocation and typed process-to-process automation.
  • Deterministic Generic Host scopes, cancellation, exit codes, logging and shutdown.
  • Native-AOT-compatible registration and JSON without reflection discovery.
  • Cross-platform command semantics, with explicit Windows GUI-subsystem console policy.
  • An adapter seam that can adopt a mature parser without leaking it into public contracts.

Non-goals

  • No shell language, pipelines, glob expansion, remote command endpoint or privilege elevation.
  • No interactive forms, full-screen terminal UI, command history or terminal emulator.
  • No dependency from the core packages to MVVM, a browser host or a specific UI framework.
  • No arbitrary object serialization, assembly scanning, service locator, or direct Environment.Exit.
  • No automatic execution of command text received through a UI transport.

Normative terms

Command definition is immutable metadata. Handler is a scoped service that executes it. Invocation is one parsed request. Human mode writes localized presentation. Machine mode writes a versioned JSON envelope. Syntax adapter converts string[] args into the library-owned invocation model. Launch classifier chooses command, UI, or error mode before the UI runtime starts. “Must” statements are release requirements; examples illustrate the required shape but may receive naming refinements through API review.

01 · Go/no-go

Adopt commodity parsing; build differentiated hosting

Phase C0 must evaluate current parser releases instead of relying on reputation or old documentation. The expected result is an adapter over an established parser. A custom parser is permitted only when the evidence below rejects every viable candidate.

01

Candidate set

Evaluate the current stable releases of System.CommandLine, Spectre.Console.Cli, Cocona, and CommandLineParser, plus a minimal in-house spike. Record package versions, licenses, transitive dependencies, maintenance activity and authoritative Native AOT guidance.

02

Reproducible spike

For each candidate, implement the same nested-command fixture, publish it with PublishAot=true, execute the full syntax corpus, measure binary size/startup, and save warnings and results under eng/cli-evaluation/. Pin SDK and package versions.

03

Keep ownership narrow

Regardless of parser choice, this library owns the immutable neutral descriptors, handler lifecycle, machine envelope, process API, console policy and Generic Host integration. Parser-specific types remain internal to an adapter package.

03 · Command model

Explicit descriptors and typed handlers

Commands form an immutable tree built during registration. The catalog owns names, aliases, parameters, localized text keys, handler type, result codec and safe diagnostic metadata; it never stores parser-native objects.

Handler

Receives typed immutable options, cancellation and a scoped execution context. It returns CommandOutcome<T> rather than writing machine JSON, assigning an exit code or calling Environment.Exit.

Context

Exposes scoped services, console, command path, output mode, culture and correlation ID. Original secret-bearing arguments are not retained in the public context.

Catalog

Command and parameter IDs are stable value objects. Definitions become immutable after validation so concurrent invocations cannot alter syntax or metadata.

Registration

Explicit builder calls or source-generated equivalents are the only supported paths. Assembly scanning and runtime handler discovery are unsupported.

Lifetime

Parsing and definition validation need no scope. A valid execution creates one async DI scope and disposes handlers/dependencies after success, fault, exception or cancellation.

Presentation

Handlers return semantic outcomes. Human renderers and the machine envelope writer consume the same outcome, preventing command logic from branching on terminal formatting.

04 · Syntax and binding

A documented portable grammar

Main(string[] args) receives already-tokenized arguments, so shell quoting is not reparsed. A raw command-line tokenizer is not part of the public API. Tests that need strings invoke the operating system or provide explicit token arrays.

Short optionOne ASCII letter, -v. Bundles such as -abc are unsupported in the portable grammar.-o result.txt

public interface ICommandSyntaxAdapter
{
    ParseOutcome Parse(
        CommandCatalog catalog,
        ReadOnlySpan<string> args,
        ParseSettings settings);
}

public sealed record ParseOutcome(
    ParsedInvocation? Invocation,
    ImmutableArray<ParseDiagnostic> Diagnostics,
    HelpRequest? HelpRequest);

Adapter rule: the adopted parser may tokenize and bind internally, but it must return the library-owned model. Parser exceptions, symbols, parse results and option types never cross a public boundary. The conformance suite runs unchanged against every adapter.

Binding and validation

Generated binders convert bound values to immutable options objects, then run generated constraints and registered async ICommandValidator<TOptions> instances. Parse diagnostics use stable codes such as CLI1001 UnknownOption; validation starts at CLI2001. Usage errors never create a command scope or call the handler.

Help and localization

Definitions store TextKey, not rendered strings. ICommandTextProvider resolves keys from a requested culture with an invariant fallback. The parser produces a neutral HelpDocument containing usage, paragraphs, parameter rows and examples; IHelpRenderer renders plain text. Width and color are capabilities, not global switches. Missing keys fail catalog validation in development and use a visible key fallback in production.

public interface ICommandTextProvider
{

}

05 · Machine output

JSON is a protocol, not console scraping

--output human|json chooses presentation; CSWEBUI_CLI_OUTPUT may supply a default but explicit arguments win. Machine mode writes exactly one UTF-8 JSON object followed by one LF. No BOM, progress bar, ANSI sequence or log line may appear on stdout.

ChannelHuman modeMachine mode
stdoutNormal command result/helpExactly one response envelope; streaming uses a distinct opt-in NDJSON protocol version
stderrErrors and actionable diagnosticsOptional operator diagnostics; never required to parse the response
loggingConfigured host providersSeparate sinks; stdout console logger is disabled or redirected
resultText/table/progress rendererProtocol, request ID, command, success, exit code, typed payload or sanitized fault
{
  "protocol": "cswebui.cli/1",
  "requestId": "01J2M6KQ7RGV9K3M5N6P8Q1T2A",
  "command": "export",
  "success": true,
  "exitCode": 0,
  "payloadType": "sample.export-result/1",
  "payload": { "written": 42, "outputPath": "result.json" },
  "fault": null,
  "diagnostics": []
}

Fault shape

fault contains stable code, safe localized message, optional safe details, and retryable. Stack traces, exception type names, environment variables and absolute internal paths are excluded unless a separately authorized diagnostic sink records them.

Exit policy

Defaults: 0 success, 2 usage/parse, 3 validation, 4 cancelled, 5 unavailable, 10 command failure, 70 host/software failure. IExitCodePolicy can remap categories but cannot turn failure into success silently.

Serialization

Each result registers JsonTypeInfo<T> and a stable payload type identifier. No supported API accepts arbitrary object graphs or invokes reflection-based JSON serialization.

Compatibility

Envelope major 1 accepts unknown additive fields. Required-field removal, semantic reinterpretation or type change requires major 2. Payload contracts version independently; clients reject unsupported identifiers before deserialization.

Request IDs

The caller may pass a validated opaque ID; otherwise the dispatcher generates one. IDs are included in logs and responses but never used as authorization or executable input.

Streaming

Not in v1. If later required, define cswebui.cli.ndjson/1 with start/event/complete records, sequence numbers and terminal outcome. Never switch a normal command to streaming implicitly.

06 · Child processes

Safe arguments, bounded output, typed responses

Process execution lives in the optional Processes package. It never invokes a shell and does not accept a single command string. Applications that intentionally need shell syntax must use a different, visibly named library.

public sealed record ProcessRequest(
    string FileName,
    ImmutableArray<string> Arguments,
    string? WorkingDirectory = null,
    ImmutableDictionary<string, string?>? Environment = null,
    TimeSpan? Timeout = null,
    int MaxStandardOutputBytes = 1_048_576,
    int MaxStandardErrorBytes = 1_048_576,
    ProcessTerminationPolicy Termination = ProcessTerminationPolicy.ProcessTree);

public interface IProcessRunner
{
    ValueTask<ProcessResult> RunAsync(
        ProcessRequest request,
        IProcessOutputObserver? observer,
        CancellationToken cancellationToken);
}

Arguments

Populate ProcessStartInfo.ArgumentList one token at a time. Empty strings, Unicode and leading-hyphen values are preserved. UseShellExecute=false is mandatory.

Executable policy

IExecutablePolicy validates resolved executable identity and optional working-directory roots before start. The default allows local trusted application calls but still rejects empty names and embedded NUL characters.

Cancellation

On timeout or cancellation, request termination once, kill the process tree where the OS supports it, await drain with a bounded grace period, and return distinct TimedOut or Cancelled state. Cancellation is never reclassified as an exit-code failure.

Output limits

Capture stdout and stderr concurrently as UTF-8 by default, with configurable encodings. Stop retaining bytes after each cap but continue draining pipes to prevent deadlock. Report truncation flags and observed byte counts.

Result

ProcessResult includes state, nullable exit code, captured channels, truncation, start exception category, start/end timestamps and duration. It does not expose a raw exception in serializable results.

Typed invocation

ITypedCommandClient<TResult> starts a known executable with machine mode, validates exit/envelope/payload versions and uses supplied JsonTypeInfo<TResult>. Malformed or oversized JSON is a protocol failure, not a command fault.

Security boundary: process execution is a local capability, not an MVVM/browser RPC method. Never bind FileName, working directory, environment keys or unfiltered argument arrays directly from web content. A host exposes named application operations that construct fixed requests after authorization and validation.
07 · Host and platform integration

Choose the mode before starting the UI

The Hosting package composes the command dispatcher with Microsoft.Extensions.Hosting. It does not know any UI framework; an application host supplies a callback for interactive mode.

HostApplicationBuilder builder = Host.CreateApplicationBuilder(args);
builder.Services.AddCsCommandLine(...);
builder.Services.AddCsCommandLineHosting(options =>
{
    options.NoArguments = LaunchMode.UserInterface;
    options.ConsolePolicy = ConsolePolicy.AttachParentOrAllocateForCommands;
});

await using IHost host = builder.Build();
return await host.RunCommandOrUiAsync(
    args,
    runUserInterface: (services, ct) => uiHost.RunAsync(services, ct),
    cancellationToken);

Classification

ILaunchClassifier returns Command, UserInterface, or Invalid using args and explicit policy. Defaults: no args → configured fallback; known command/help/version/output switch → command; unknown leading token → usage error, never silent UI fallback.

Host lifetime

Build and validate once. Command execution creates one async scope, awaits disposal, flushes logs, returns the exit code and stops the host. UI mode delegates lifetime to the UI callback. A handler never stops the process directly.

Console abstraction

ICommandConsole exposes input, output, error, redirection, interactivity, width, encoding and color capability. Tests use memory streams. Rendering honors NO_COLOR, redirection and explicit configuration.

Windows GUI executable

Console policy is explicit: inherit existing console; attempt AttachConsole(ATTACH_PARENT_PROCESS) for command mode; optionally allocate a console only when configured. P/Invoke resides in an internal Windows implementation with generated marshalling. Failure degrades to redirected streams or a structured host error.

Unix/macOS

Use inherited standard handles and terminal detection; never allocate a terminal. Signals feed cancellation through host lifetime. Process-tree termination behavior is capability-tested and documented per runtime identifier.

Headless/service use

When no interactive UI fallback is registered, no args produces help/usage according to policy. Non-interactive input disables prompts. The command core never waits for input unless a handler explicitly requests it and IsInteractive is true.

Composition contract: the future all-in-one application host references this Hosting adapter and the UI/MVVM host. This library remains independently usable in console tools and test processes, preventing a dependency cycle.
08 · Diagnostics and operations

Stable errors outside, rich telemetry inside

Consumer-visible diagnostics are safe, stable records. Internal logs carry technical detail under the same correlation ID, subject to redaction and host policy.

AreaRequired behavior
Parse diagnosticsStable code, severity, token index, command path, localized message key and safe arguments. Never include secret option values.
LoggingStructured events for classification, parse, validation, handler start/stop, outcome and process start/stop. Argument values are omitted by default; definitions may mark safe values explicitly.
Metrics/tracingOptional ActivitySource and Meter with command name, outcome and duration. Do not record payloads, paths or request arguments as tags.
ExceptionsExpected faults use CommandOutcome. Unexpected exceptions are logged, mapped to sanitized CLI5000, and return host/software failure. Fatal runtime exceptions are not swallowed.
SecretsOptions can be marked Sensitive; help may describe them, but diagnostics, logs and generated command previews always redact their values.
ConcurrencyRegistry is immutable and thread-safe. Invocations have independent scopes/consoles. Process-global culture, current directory, console streams and environment are never mutated.

10 · Roadmap

The evaluation is mandatory. If an established parser satisfies the requirements, redirect parser effort toward the adapter, protocol and host behavior rather than recreating parsing.

11 · Definition of done

Acceptance for a public 1.0

Release only when every item below is evidenced in the repository and repeatable from a clean machine using public dependencies.

Architecture and API

  • The parser decision ADR and reproducible evaluation are committed.
  • All supported public types have XML documentation and API approval baselines.
  • No parser-specific type appears in Abstractions, handlers or application examples.
  • Package dependency direction matches this plan; the core has no UI/MVVM dependency.
  • Registration validation reports all catalog errors before invocation.

Behavior and protocol

  • The entire syntax/help/localization corpus passes against the selected adapter.
  • Human and machine outputs are byte-tested; machine stdout contains one valid envelope.
  • Exit categories and stable diagnostic codes are documented and tested.
  • Process runner bounds output, preserves arguments and distinguishes cancellation, timeout, start and exit failures.
  • Windows GUI launch classification and console attachment are covered by executable integration fixtures.

AOT, security and operations

  • Packed smoke applications publish and execute Native AOT with zero trim/AOT warnings.
  • No assembly scan, runtime code generation, reflection JSON or descriptor file is required.
  • A threat model covers argument injection, process capability exposure, secret redaction, protocol abuse and output exhaustion.
  • Structured logs, activities and metrics contain no argument/payload data by default.
  • Dependency/license inventory and vulnerability scanning are part of CI.

Documentation and adoption

  • Quick start, command authoring, generated registration, localization, JSON client, process runner and host/UI coexistence guides compile as samples.
  • At least one console-only sample and one dual UI/CLI sample restore exclusively from locally packed packages.
  • Two independently shaped sample applications exercise the public extension seams.
  • Compatibility and support policy covers syntax, diagnostics, exit codes, envelope and payload contracts.
  • The implementation can be reproduced without access to the systems that motivated this plan.
1.0 outcome: application authors can add typed hosted commands and machine automation to a Native-AOT UI application without owning parser plumbing, leaking parser types, scanning assemblies, contaminating stdout, concatenating shell commands or coupling command handling to a UI framework.
