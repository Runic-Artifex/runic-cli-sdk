# Runic Command Line 0.9.1

A security patch of 0.9.0 with fixes from the Command Line security review. It
has no public API changes. Some of the fixes change behaviour; the sections
below say what changes and what to do.

## Security fix: bare tool names never run from the current directory (SEC-38)

- `ProcessRunner` now looks up a bare executable name, such as `gh` or `npm`,
  only in the absolute entries of the effective `PATH` (the request's own
  `PATH`, or the parent's when `InheritEnvironment` is true and the request
  does not set one), with the `PATHEXT` extensions on Windows. Relative
  entries such as `.` are skipped. The child starts with the full path that
  was found.
- **Behaviour change:** a bare name without a match on `PATH` now ends in
  `ProcessState.StartFailed` with `ProcessStartFailureCategory.NotFound`
  (`RCLI6005`) before the executable policy runs. Before, it started a file
  of that name from the current directory or the application directory, so a file planted in a cloned repository or an extracted archive
  could stand in for a tool that is not installed. This holds with and
  without `InheritEnvironment`, on every operating system.
- To run a tool from the current directory on purpose, name it as a path:
  `./tool` (Windows: `.\tool.exe`). A name with a directory separator still
  resolves against the current directory, and an absolute path is used as
  given.
- On Windows, a bare name that already has a dot, such as `python3.12` or
  `My.Tool`, is tried as given and then with each `PATHEXT` extension, so
  `My.Tool` finds `My.Tool.exe` on `PATH`.

## Security fix: invisible and reordering characters in faults (SEC-40)

- Faults, diagnostics, echoed tokens, the lines of a `CommandTaskLog` or
  spinner and the developer exception output no longer pass on the characters
  that can reorder or hide text on a terminal (Trojan Source): the
  bidirectional embeddings and overrides U+202A–U+202E, the isolates
  U+2066–U+2069, the tag characters U+E0000–U+E007F, and U+200B, U+2060 and
  U+FEFF. In fault and diagnostic text, human or JSON, each run of them
  becomes a space; a `CommandTaskLog` line drops them; an echoed unknown
  token that contains one is shown as `<invalid>`. The joiners and direction
  marks that Persian, Indic and right-to-left text and emoji need (ZWNJ, ZWJ,
  LRM, RLM and ALM, U+200C–U+200F and U+061C) are kept.
- **Behaviour change for readers:** the protocol now counts these characters
  among its Unicode control characters. `CommandJsonEnvelopeReader.Read<T>`
  and `CommandTestEnvelope.Read<T>` reject a frame that carries one in fault
  text (`unsafe-fault-content`), diagnostic text
  (`unsafe-diagnostic-content`) or its request ID (`invalid-request-id`), as
  they already rejected C0 and C1 controls. A request or correlation ID that
  contains one is rejected like one with a control character. Frames written
  by Command Line 0.9.1 never carry them there; a frame from 0.9.0 or another
  producer that does is now a `CommandProtocolException`.

## Other security fixes

- **Children of an interrupted run (SEC-39).** When the process exits while
  a `ProcessRunner` run has not returned, for example through
  `Environment.Exit` on a repeated Ctrl+C or SIGTERM in `CommandApp`, or when
  `Main` returns with a run pending, the runner now kills that run's child and
  its process group or job. Before, the child kept running. On Windows the job
  also ends the child when the parent ends without running exit handlers. A
  descendant that outlives a child that exited normally is left running, as
  before. A child that needs its grace period gets it only when the command
  holds `CommandExecutionContext.ProtectShutdown()` around the whole `RunAsync`
  call. `SIGHUP` is still not handled: when the terminal closes, a Unix child
  in a process group of its own can outlive the application.
- **Bounded response files (SEC-41).** Expanding `@file` arguments is limited
  to 1 MiB per file and to 4 MiB and 65,536 arguments for all response files
  of a command line together. Breaking a bound, as `@/dev/zero` does, is the
  existing usage error `RCLI1017` (`response-file-unreadable`) instead of
  running out of memory. Files are read in chunks, so a pipe such as
  `@/dev/stdin` still works.
- **Developer exception output (SEC-42).** The exception text that
  `RUNIC_COMMANDLINE_DEBUG=1`, `DOTNET_ENVIRONMENT=Development` or an attached
  debugger writes to standard error keeps line breaks and tabs, but no other
  control characters (carriage returns included) or the characters of SEC-40.
  It is still not redacted: keep both variables unset where standard error is
  collected, such as in CI.
- **Duplicate payload members (SEC-43).** The strict readers reject a frame
  with a duplicate member anywhere inside `payload` (`duplicate-property`), as
  the protocol already required, instead of keeping the last value.
- **Windows batch detection (SEC-44).** A batch file named with an NTFS stream
  suffix, such as `tool.cmd::$DATA`, is now recognized and rejected with
  `RCLI6007` unless batch files are allowed, like `tool.cmd`.

## Documentation

- `SECURITY.md` lists the behaviour Runic tools rely on, and the Processes
  README has a new "Executable resolution" section. The first Processes
  example now runs its tool with `InheritEnvironment = false` and a minimal
  environment, since an inherited environment passes on credentials such as
  `GITHUB_TOKEN` in CI (SEC-46). The READMEs name which output is sanitized
  (faults, diagnostics, task-log and spinner lines) and which is written as
  given (a payload's human output, `HumanOutput`, and captured or streamed
  child output) (SEC-47).
