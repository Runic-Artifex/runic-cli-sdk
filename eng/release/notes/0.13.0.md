# Runic Command Line 0.13.0

Command Line 0.13.0 is the first release of the 0.19 release train (Command
Line 0.13.0, then Runic Translations 0.11.0, then Runic SDK 0.19.0). It makes
help and usage texts read the way users see the command line. The API changes
are additive; package validation against 0.12.0 is clean. Some help and usage
output changes; the changes are listed under
[Upgrading from 0.12](#upgrading-from-012).

## Upgrading from 0.12

Nothing is removed. These changes can still need action:

| Change | Who is affected | What to do |
| --- | --- | --- |
| The missing-argument error names the argument as the usage line shows it: `The <destination> argument is missing.` (was `The destination argument is missing.`); its JSON `arguments` are `["<destination>"]` | Tests and JSON consumers that compare the message or `arguments` of `RCLI1005` | Expect the placeholder. Kind, code and `messageKey` (`diagnostics.missing-argument`) are unchanged; a translation that shows `{argument}` shows the placeholder too. |
| Help shows no `[default: False]` for Boolean options, and no default for any option that takes no value; a generated Boolean option's `CommandHelp.DefaultValue` is null | Tests that compare help text or read `DefaultValue` of a flag | Update the expected help; treat a flag's default as off. |
| Help lists arguments as `<value-name>` under "Arguments" (was the argument's name, such as `container-path`), and names options in `[requires: …]` and `[conflicts: …]` by their spelling in the catalog's dialect, such as `--factor` or `/factor` (was the option ID, such as `factor`) | Tests that compare help text | Update the expected help. |

German text for this release needs `Runic.Translations.CommandLine` 0.11.0.
Each Command Line minor has one adapter release line, released right after it in
the same train:

| 0.12.x | 0.10.x (Runic.CommandLine `[0.12.0, 0.13.0-0.0)`) |
| 0.10.x, 0.11.x | none; 0.9.1 does not accept them (`NU1608`) |

## A text key for extended help (#97)

- `[Command]` and `[CommandGroup]` take `LongDescriptionKey`, the localization
  key of `LongDescription`, as `DescriptionKey` is of `Description`. Help
  resolves it through the application's `ICommandTextResolver` and shows
  `LongDescription` when the key is not translated. The resolved text keeps its
  paragraphs, line breaks and preformatted lines, as the literal does:

  ```csharp
  [Command("policy alias", DescriptionKey = "commands.policy-alias", Description = "Set up aliases.",
      LongDescriptionKey = "commands.policy-alias.details", LongDescription = "A restart is required afterwards.")]
  ```

- Without the generator, set `CommandHelp.LongDescriptionKey`.
  `CommandTextContext.LongDescription(help)` resolves it for custom help
  presenters.
- `CommandTextContext.ValidateDescriptionKeys` reports an unresolved
  `LongDescriptionKey` as `RCLI0023`, the catalog rejects an empty one as
  `RCLI0003`, and the generator reports an empty, overlong or control-character
  key as `RCLI9005`, as for `DescriptionKey`.

## Help and usage errors name what users see (#98)

Users read an argument as its value name in the usage line and an option as its
spelling. Help and usage errors no longer name them by their internal ID, which
comes from the C# parameter name and appears nowhere else in the output:

```text
$ tool.exe /policy /link one
The <Container-Pfad> argument is missing.
Usage: tool.exe /policy /link <Richtlinie> <Container-Pfad> [options]

$ tool.exe /policy /link /?
Arguments:
  <Richtlinie>      [required]
  <Container-Pfad>  [required]

$ tool.exe /policy /alias /?
  /r <AltName>          Entfernt die Einträge für <AltName> [conflicts: /l]
```

- The missing-argument error (`RCLI1005`, `diagnostics.missing-argument`) names
  the argument by its value name, or else its name, in angle brackets, as value
  errors such as `invalid-integer` already did.
- The "Arguments" section of help lists the same placeholders.
- `[requires: …]` and `[conflicts: …]` name options by their primary spelling in
  the catalog's dialect, as the usage error for the same relation already did
  (`/r cannot be combined with /l.`).
- IDs stay where programs read them: `ConflictsWith` and `Requires`
  declarations, binding IDs and `CommandHelp.Requires`/`ConflictsWith`.
- No text key is added and no English template changes; the keys receive the
  names users see as their arguments.

## No default for flags in help (#99)

A Boolean option is a presence flag, and `RCLI9024` already forbids a `true`
default, so `[default: False]` told users nothing, and in localized help it was
the untranslated `bool.ToString()`. Help now shows no default for an option that
takes no value, whether or not the C# parameter declares `= false`, and the
generator no longer records one in `CommandHelp.DefaultValue`. Value options
keep their defaults, such as `[default: 1.5]`.

`= false` stays allowed and is not reported: it lets C# callers and tests call
the command method without the argument, and lets the flag follow other
parameters with defaults.
