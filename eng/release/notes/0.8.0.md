# Runic Command Line 0.8.0

## Plain 0.y.z versions

- From 0.8.0 Command Line releases use plain `0.y.z` versions until 1.0, as the
  Runic SDK does: a new minor (`0.9.0`) may contain breaking changes, a patch
  (`0.8.1`) only fixes or adds, and only the latest minor gets fixes. Releases
  are still marked as prereleases on GitHub.
- NuGet treats `0.8.0` as a stable version: install and update without
  `--prerelease`. A floating `0.*` range now resolves to it.
- The generator's analyzer release headers are the plain version
  (`## Release 0.8.0`).

## Spectre.Console range

- `Runic.CommandLine.Spectre` depends on Spectre.Console `[0.57.2, 0.58)`
  instead of `>= 0.57.2`. Spectre.Console types are part of its public API and
  Spectre.Console is pre-1.0, so a new Spectre.Console minor may change them;
  the range moves in a Command Line minor after testing. An application that
  references a newer Spectre.Console directly gets NuGet warning `NU1608` and
  runs an untested combination.

## camelCase command results (`RCLI9044`)

- The generator warns with `RCLI9044` when a `[CommandResult]` names a
  `JsonSerializerContext` that does not select camelCase property names, either
  with `[JsonSourceGenerationOptions(PropertyNamingPolicy = JsonKnownNamingPolicy.CamelCase)]`
  or with `[JsonSourceGenerationOptions(JsonSerializerDefaults.Web)]`. Such a
  payload was written with the C# property names (`{"Status":…}`) inside the
  camelCase `runic.commandline/1` envelope. Results without property names
  (numbers, strings, enums, GUIDs and lists of them) are not reported.
- To fix it, add the option to the context. To keep a published payload as it
  is, suppress the warning with `#pragma warning disable RCLI9044` around the
  `[CommandResult]` or `<NoWarn>$(NoWarn);RCLI9044</NoWarn>`. A build that
  treats warnings as errors fails until one of these is done.

## Behaviour change: camelCase renames JSON payloads and human rows

Switching a result context to camelCase changes two outputs of every command
that uses it:

- **JSON:** the payload's property names in the `runic.commandline/1` envelope
  and in a payload-shaped `--json` alias (`{"Status":"Ready"}` becomes
  `{"status":"Ready"}`). Update every consumer of that payload type, or keep the
  old names by suppressing `RCLI9044` and leaving the context unchanged.
- **Human output:** the default human output of a typed result prints one
  `name: value` row per JSON property, so its labels follow the same names
  (`Status: Ready` becomes `status: Ready`). Human output is not a contract, but
  scripts or snapshots that match it change. To keep the old rows while the
  JSON moves to camelCase, register a human presenter for the command with
  `GeneratedCommandCatalog.Create(builder => builder.Present<Report>("report", …))`,
  which writes its own text and leaves the JSON unchanged. Commands with a
  presenter, `string` results and results without properties are not affected.

In this repository the transform example, the tests, the NativeAOT smoke and
the package consumer switched to camelCase; the transform example registers
its own human output, so only its JSON changed.
- The diagnostics guide allocates the application range `RCLI8000`–`RCLI8999`
  per Runic tool: `RCLI81xx` `dotnet runic`, `RCLI82xx` `runic-translations`,
  `RCLI83xx` `runic-create`; the rest is free for applications. Protocol
  `runic.commandline/1` is unchanged.

## Generator loads on every .NET 10 SDK

- The generator is compiled against the compiler of the lowest .NET 10 SDK
  feature band (Microsoft.CodeAnalysis 5.0.0, SDK 10.0.1xx) instead of the
  building SDK's (5.9.0 in SDK 10.0.4xx). With earlier packages a build on SDK
  10.0.1xx reported `CS9057` and `Runic.CommandLine.Generated` was missing.
- The generator needs a .NET 10 SDK compiler: `dotnet build`, Visual Studio with
  the SDK's compiler, Rider or the C# Dev Kit. Visual Studio's .NET Framework
  MSBuild compiler cannot load it (`CS8032`); the core README says so.

## Documentation

- The core README documents that `CreateScopeFactory` wins over `ScopeFactory`
  when both are set, and that `CommandTestEnvelope.Parse` checks only the
  framing of a response; `CommandJsonEnvelopeReader.Read<T>` validates it.
- The Spectre README no longer says that prompts return a fallback without
  interaction: a `CommandPrompts` question without a default fails with
  `RCLI4001`.
- The Processes README states that the runner runs a child to completion and
  does not supervise long-running children.
- The release guide lists the API rules Command Line keeps until 1.0 and plans
  the `linux-arm64`, `win-arm64`, `linux-musl-x64` and `linux-musl-arm64`
  NativeAOT runtimes for 0.9.0, the additive Command Line release.

## Output selector: --format, declared on the catalog

- The option that selects human or JSON output is now `--format` instead of
  `--output`, and the catalog declares it:
  `CommandCatalogBuilder.OutputSelector(string name, params IEnumerable<string> hiddenAliases)`.
  `CommandCatalog.OutputSelector` and `CommandCatalog.OutputSelectorAliases`
  report it. Help, completion scripts, `CommandCompletion.Query`, `CommandApp`
  and the hosting adapter all read it from the catalog, so they can no longer
  disagree. `RUNIC_COMMANDLINE_OUTPUT` is unchanged.
- Hidden aliases keep former spellings working
  ([#63](https://github.com/Runic-Artifex/runic-cli-sdk/issues/63)):
  `OutputSelector("--format", "--output")` accepts `tool list --output json`
  as `tool list --format json`. An alias parses exactly like the selector
  (separated or `=` value, also before the command, not after `--`). Help,
  completions and suggestions show only the selector, and diagnostics about
  the value (`RCLI1003`, `RCLI1010`) name the selector. Two different
  spellings are `RCLI1016`, the same spelling twice is `RCLI1007`.
- New catalog validation code `RCLI0026`: a command option spelled like the
  selector or one of its hidden aliases, including an option named `--format`
  when the catalog declares no selector, and `CommandCatalog.Combine` of
  catalogs that declare different selectors. A catalog that declares none
  takes the declared one. `RCLI0024` now reports a JSON output alias spelled
  like the selector or an alias (the rule that the alias cannot be `--output`
  is gone), and `RCLI0025` a completion option spelled like either.
- New generator warning `RCLI9045`: a generated command's `[Option]` named
  `--format` or with a `--format` alias, so the break shows up at compile time
  rather than as `RCLI0026` on first run. The generator cannot see a selector
  declared at run time; suppress the warning where the application declares
  another selector with `OutputSelector(...)`. `--output` is not reported.
- The spelling is no longer a parse setting. Removed:
  `ParseSettings(..., transportOutputOptionName)` and
  `ParseSettings.TransportOutputOptionName`, the same parameter and property of
  `HostedCommandLineLaunchInput`, and the `outputOptionName` parameters of
  `ICommandHelpPresenter.WriteAsync`, `CommandHelpFormatter.Format`,
  `CommandCompletion.Generate` and `CommandCompletion.Query`.
  `ICommandHelpPresenter` has one `WriteAsync` member, with a
  `CommandTextContext`, and no default implementation.

## Exit codes

- The default exit codes are those of every Runic tool: 1 for an expected
  failure, 2 for usage, 3 for an unexpected failure and 130 for a cancelled
  command, as a shell reports an interrupted one.
  `CommandExitCodes` and the default `IExitCodePolicy` follow.
- `CommandExitCategory`, the JSON fault and observers still distinguish every
  category. A custom `IExitCodePolicy` can give categories distinct codes.
- A repeated termination signal still exits at once with 128 plus the signal
  number (130, 131 or 143).

## Termination signals

- `CommandApp.HandleCancelKeyPress` is renamed `HandleTerminationSignals`; it
  covers Ctrl+C (SIGINT), SIGTERM and SIGQUIT, as before.
- `CommandExecutionContext.ProtectShutdown()` returns a scope that keeps a
  repeated signal from exiting the process while cleanup that must finish runs,
  such as stopping child process trees or removing what the command created.
  The invocation stays cancelled; after the last scope is disposed the next
  signal exits again. It has no effect when `CommandApp` does not handle the
  signals (`HandleTerminationSignals = false`, the hosting adapter or a
  directly used `CommandExecutor`).

## Testing

- `CommandTestEnvironment.Capture(IReadOnlyDictionary<string, string?>? variables = null)`
  replaces `CommandTestEnvironment.ParseSettings(string? output)`. It builds
  settings the way `CommandApp` captures them from the process environment,
  from the dictionary only: `RUNIC_COMMANDLINE_OUTPUT` selects the output
  mode, and `RUNIC_COMMANDLINE_NO_INPUT` and option environment fallbacks read
  the same entries. The process environment is never read.

- `GeneratedCommandCatalog.Create(b => b.OutputSelector("--output"))` keeps
  the old spelling exactly; help and completions keep showing `--output`.
- `GeneratedCommandCatalog.Create(b => b.OutputSelector("--format", "--output"))`
  adopts `--format` and keeps accepting `--output` as a hidden alias.
- An application with its own `--format` option declares another selector, for
  example `OutputSelector("--output")` or `OutputSelector("--runic-output")`.
- `CommandExitCodes` members are constants, so code compiled against 0.7
  keeps the old numbers until it is rebuilt. To keep the old codes, supply an
  `IExitCodePolicy` that returns 3, 4, 5, 10 and 70 for `Validation`,
  `Cancelled`, `Unavailable`, `CommandFailure` and `HostFailure`, to
  `CommandApp.ExitCodePolicy` and to the `CommandExecutor` of a hosting adapter.
- Scripts that test `-eq 4` (cancelled), `-eq 10` (command failure), `-eq 5`
  (unavailable), `-eq 3` (validation) or `-eq 70` (host failure) test 130, 1,
  1, 2 and 3 instead, or read the JSON fault code when they must tell
  categories that now share a code apart.
- A custom `ICommandHelpPresenter` implements the one `WriteAsync` member and
  takes the selector from `catalog.OutputSelector`.

## API cleanup before 1.0

The 1.0 API review removes preview-era overloads and duplicates, so each
operation has one member. Everything below is a source break; rebuild against
0.8.0. The `runic.commandline/1` wire format is unchanged.

### One member per operation

- `CommandOutcome.Failure<T>(category, fault, diagnostics = null, humanOutput = null, failureData = null)`
  replaces the three `Failure` overloads and `FailureWithData`.
- `CommandResponse.Failure<T>(requestId, command, exitCode, fault, diagnostics = null, failureData = null)`
  replaces `Failed` and `FailedWithData`; `CommandResponse.Success<T>` replaces
  `Succeeded`.
- `CommandOutputDispatcher.DispatchAsync<T>(mode, console, culture, response, codec, textContext = null, cancellationToken = default)`
  is the only dispatch member.
- `CommandBuilder.Option(id, name, arity, repeatPolicy = Error, isSensitive = false, descriptionKey = null, isRequired = false, params aliases)`
  is the only option member. The overload with a positional `bool? isRequired`
  is gone; pass `isRequired:` by name.
- `IProcessRunner.RunAsync(request, outputHandler = null, cancellationToken = default)`
  is the only member, on `ProcessRunner` as well. It has no default
  implementation that replays a capture: a test double implements it and passes
  its own capture to the handler. Pass a token without a handler by name.
- `IProcessObserver.OnStarted(ProcessIdentity, DateTimeOffset)` is the only start
  notification.

### Succeeded

`Succeeded` replaces `IsSuccess` on `CommandOutcome<T>`, `CommandExecutionResult`
and `HostedCommandLineExecutionResult`, and `Success` on `CommandResponse<T>`. The
envelope key stays `success`.

### Removed and renamed

- `CliProtocol` is renamed `CommandProtocol`; `CommandProtocol.Identity` is still
  `runic.commandline/1`.
- `CommandParsePresentation` is internal; `CommandApp` and the hosting adapter
  present parse outcomes.
- `IHostedCommandLineAdapter` is removed; hosts use `CommandLineHostingAdapter`.
  `HostedCommandLineDecision` has no public constructor: decisions come from
  `Classify`.
- `CommandApp.FormatHelp` and `CommandPresentation.FormatHelp` are removed; use
  `HelpPresenter` (an `ICommandHelpPresenter`).
- Testing: `CommandTestCancellation` and `TestExecutionScopeFactory` are removed.
- `SpectreCommandConsole.PromptAsync` is removed; use `CommandPrompts`.
- `ProcessExecutionOptions.MaximumOutputLimitBytes` and
  `ProcessStandardInput.MaximumInputLimitBytes` are static get-only properties
  instead of constants, so a later release can raise them without rebuilding
  callers. The value is still 16 MiB.

### Generated code

- The generated `GeneratedCommandCatalog` is `internal` and marked
  `[GeneratedCode]`. Another assembly, such as a test project, uses a public
  method of the assembly that declares the commands, as the WPF example's
  `ReportCommandApp.Create` does.
- `GeneratedCommandBinding` and `GeneratedCommandBindingException` moved to
  `Runic.CommandLine.Generated` and are hidden from IntelliSense. They are a
  support API for code generated by the generator of the same major version,
  not for hand-written calls.

### Enum zero values

- `CommandDiagnosticSeverity` is `Information = 0`, `Warning = 1`, `Error = 2`
  (was `Error = 0`, `Warning = 1`, `Information = 2`), so `default` is the
  mildest severity.
- `ProcessStartFailureCategory` is `Other = 0`, `NotFound = 1`,
  `AccessDenied = 2`, `InvalidRequest = 3`, `Unsupported = 4` (was
  `NotFound = 0` … `Other = 4`).
- The names are unchanged: the envelope still writes `error`, `warning` and
  `information`, and a start fault's `category` detail is still the member name.
- Every public enum and string set now states in its documentation whether it is
  open or closed.

### Reserved command name `root`

`root` is reserved like `help`, `version` and `output`: `RCLI0002` at catalog
validation and `RCLI9001` from the generator. The envelope's `command` value is
`root` for root-level parse errors and `help` or `version` for framework
responses, so a command may not be named that.

- Positional `bool? isRequired` caveat: the removed overload took a `bool?`
  right after the repeat policy, and overload resolution picked it only for a
  `bool?` value there or for `isRequired:` by name. A call that passes a `bool?`
  variable positionally, such as
  `.Option("name", "--name", arity, CommandOptionRepeatPolicy.Error, required, "-n")`,
  no longer compiles; write `isRequired: required ?? false, aliases: ["-n"]`. A
  `bool` literal in that position selected `isSensitive` in 0.7 and still does:
  `.Option(..., CommandOptionRepeatPolicy.Error, true, "-n")` is a sensitive,
  optional option with description key `-n` and no alias, so check such calls
  and name the parameters. Calls with `isRequired:` by name compile unchanged.
- Enum members are constants: a binary compiled against 0.7 that passes or
  compares `CommandDiagnosticSeverity` or `ProcessStartFailureCategory` values
  reads them with the old numbers until it is rebuilt. Code that stored the
  numbers, for example in logs or settings, maps them by name.
- `RunAsync(request, token)` against `IProcessRunner` no longer compiles,
  because the second parameter is the handler; name the token.
