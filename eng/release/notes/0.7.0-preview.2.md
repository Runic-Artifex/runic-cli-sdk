# Runic Command Line 0.7.0-preview.2

## Generator diagnostics

- `RCLI9003` (unsupported generated command type) names the reason as well as
  the parameter and its type: an argument or option type that cannot be bound,
  a Boolean positional argument, an inaccessible `[FromServices]` type, or a
  type the command generator cannot resolve. The last one covers a type emitted
  by another source generator, such as a Runic Translations text class like
  `HelloText` used as a `[FromServices]` parameter: source generators do not
  see each other's output. The message says to inject a type declared in source
  or a referenced assembly instead, for Runic Translations `ITranslationManager`,
  and create the text class from it in the command
  ([#28](https://github.com/Runic-Artifex/runic-cli-sdk/issues/28)). The same
  parameters fail as before; only a `[ConvertWith]` argument or option whose
  type cannot be resolved now reports `RCLI9003` instead of `RCLI9030`.

## `CommandUnit` results need no metadata

- A generated command that returns `CommandUnit`, `CommandOutcome<CommandUnit>`
  or either wrapped in `Task<T>` or `ValueTask<T>` no longer needs
  `[CommandResult]` (`RCLI9028`)
  ([#45](https://github.com/Runic-Artifex/runic-cli-sdk/issues/45)). It uses
  `CommandResultCodecs.Unit` and the payload type `runic.unit/1`, and writes
  exactly what a `void` command writes, so a command that only reports failures
  through `CommandOutcome` can return `CommandOutcome<CommandUnit>`. An explicit
  `[CommandResult]` still selects its own payload type and JSON context.

## A JSON output alias that writes the bare payload

- `CommandCatalogBuilder.JsonOutputAlias("--json", JsonOutputShape.Payload)`
  declares the alias for an application whose existing `--json` consumers read
  the bare document rather than a `runic.commandline/1` envelope
  ([#41](https://github.com/Runic-Artifex/runic-cli-sdk/issues/41)). With the
  flag, a command writes its success payload, serialized with its result
  metadata, and one LF to standard output and nothing else; a command without a
  result writes nothing. A failed or cancelled command writes the payload of its
  declared failure data the same way, or nothing. On standard error it writes
  its diagnostics as human text, then its `humanOutput` exactly in place of the
  `CODE: message` fault line, or the fault line when it supplied none. Exit codes
  are those of the envelope.
- Help, version and usage errors on a command line that gives the flag are human
  text, so `tool --bogus --json` writes its error to standard error, as legacy
  contracts expect. `--output json` and `RUNIC_COMMANDLINE_OUTPUT=json` keep
  writing the envelope.
- Failure data keeps its 65,536-byte bound, because the same outcome can also be
  written as an envelope. A success payload is not bound by the protocol's frame
  limit.
- Help describes a payload-shaped alias as "Write the result as JSON" (text key
  `help.json-payload-output-alias`). `CommandOutputClassification.Shape` and
  `CommandExecutionContext.OutputShape` report the shape to hosts, handlers and
  custom outcome sinks. Combined catalogs that declare the same alias with
  different shapes fail validation with `RCLI0024`.
- `JsonOutputAlias(string)` and its envelope are unchanged.

## A continuation on the thread that called `CommandApp.Run`

- A command can hand a synchronous continuation back to `Main` with
  `CommandExecutionContext.ContinueOnCallingThread(Func<int>)`, for example to
  start a desktop host that must own the main thread before any `await`
  ([Runic-Artifex/runic-sdk#301](https://github.com/Runic-Artifex/runic-sdk/issues/301)).
- `CommandApp.Run(string[], CancellationToken)` runs the invocation as `RunAsync`
  does, blocking the calling thread, then invokes the continuation on that thread
  and returns its result as the exit code. The continuation runs only after a
  successful invocation that was not cancelled, after its output was written and
  its scope disposed. The invocation runs without the caller's
  `SynchronizationContext`.
- `Runic.CommandLine.Testing`: `CommandAppTester.Run(string[], CancellationToken)`
  is the synchronous counterpart of `RunAsync` and runs the continuation on the
  calling thread, so applications can test commands that hand one back.
- `CommandExecutionContext.CanContinueOnCallingThread` is false under `RunAsync`,
  the hosting adapter and a directly used `CommandExecutor`, where
  `ContinueOnCallingThread` throws. The hosting adapter does not own the entry
  point or its thread; [#52](https://github.com/Runic-Artifex/runic-cli-sdk/issues/52)
  tracks support there.
