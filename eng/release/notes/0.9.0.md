# Runic Command Line 0.9.0

## Outcome presenters

- `CommandCatalogBuilder.PresentOutcome<T>(path, presenter)` registers human
  output for a command's whole outcome, success or failure. The
  `CommandOutcomePresenter<T>` receives a `CommandOutcomePresentation<T>` with
  the `Outcome`, `ExitCode`, the binding and outcome `Diagnostics`, the
  `Command` and the invocation's `Context`; `WriteDefaultAsync` writes the
  output the application's outcome sink would have written. The presenter runs
  only in human mode, in place of the outcome sink; JSON output is unchanged.
  An application that implements `ICommandOutcomeSink` only to change the human
  output of some commands can register presenters instead. `ICommandOutcomeSink`
  keeps working.
- A presenter's result type must match the command's (`RCLI0020`, as for
  `Present<T>`).

## Response files

- `CommandCatalogBuilder.ResponseFiles()` lets an application read arguments
  from response files: `tool @build.rsp` runs as if the arguments in
  `build.rsp` had been given in its place. It is off by default, and
  `CommandCatalog.ResponseFiles` tells whether a catalog declared it;
  `CommandCatalog.Combine` reads them when one part does. `CommandApp` and
  `CommandLineHostingAdapter.Classify` expand the arguments before parsing.
- A response file is strict UTF-8, with or without a byte order mark. Lines
  whose first non-blank character is `#` are comments, arguments are quoted
  with the Windows (MSVCRT) rules, `@file` inside a response file is relative
  to that file's directory, files nest at most 16 levels deep and may not
  include themselves, and `@@` stands for a literal leading `@`. These are the
  rules of `runic-translations`' own expander, which can now use the library.
- A file that cannot be used is a usage error with a new parser code:
  `RCLI1017` (cannot be read), `RCLI1018` (not valid UTF-8), `RCLI1019`
  (unterminated quote), `RCLI1020` (nested more than 16 levels) and
  `RCLI1021` (includes itself). Their messages are the new text keys
  `diagnostics.response-file-unreadable`, `-invalid-utf8`,
  `-unterminated-quote`, `-too-deep` and `-cycle`, with the argument `file`.
- Help lists `@<file>` (text key `help.response-files`), and the generated
  bash, zsh, fish and PowerShell completions, like `CommandCompletion.Query`,
  complete a file name after `@`. A catalog without the declaration writes
  the same help and completion scripts as before.

## Strict envelope reading in tests

- `CommandTestEnvelope.Read<T>(json, typeInfo)` in `Runic.CommandLine.Testing`
  reads a captured JSON response and returns the `CommandResponse<T>` with its
  typed payload. It applies every check of `CommandJsonEnvelopeReader.Read<T>`
  (framing, limits, required members and their types, duplicates, the success
  and failure rules) and also rejects members the protocol does not define on
  the envelope, the fault, the fault's `data` and diagnostics, with the
  `CommandProtocolException` kind `unknown-member`. The payload is read with the
  supplied `JsonTypeInfo<T>` only, so tests stay trim- and NativeAOT-safe.
  `CommandTestEnvelope.Parse` still checks the framing only.

## Behaviour change: the outcome sink's context carries the handler's state

- The `CommandExecutionContext` passed to `ICommandOutcomeSink.WriteAsync` (and
  to an outcome presenter) now carries the handler's state instead of fresh
  defaults: its `TextResolver`, whether `RUNIC_COMMANDLINE_NO_INPUT` disabled
  prompts, its continuation and its shutdown protection. Before, a sink saw no
  text resolver, `new CommandPrompts(context).IsInteractive` ignored
  `RUNIC_COMMANDLINE_NO_INPUT`, `CanContinueOnCallingThread` was false and
  `ProtectShutdown()` had no effect. A sink that relied on those defaults now
  sees the invocation's values. No code change is needed.
