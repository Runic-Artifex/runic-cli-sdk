# Runic Command Line 0.15.0

## A protocol corpus that any implementation can run (D080, R7 G12)

The `runic.commandline/1` specification and its corpus no longer rely on the .NET test runner for anything they
check. Nothing changes for applications: the library, its JSON output and its reader behave as in 0.14.

- **Value-normative examples.** The examples are compared by JSON value. Byte identity is required only of a writer
  that claims the named `dotnet` escaping profile, which the protocol README now defines exactly, including the fault
  detail order (UTF-16 code units). Another writer may escape differently and still conform.
- **Writer cases.** `protocol/writer-cases.json` gives the inputs that produce each example, and cases for the
  sanitization steps, so a writer in another language can replay them. A tenth example,
  `examples/fault-details.json`, covers detail sanitization, ordering and escaping outside ASCII.
- **Sanitization, specified.** The README now gives the exact algorithm for faults and diagnostics, instead of
  calling it a heuristic: control-character runs, truncation on scalar boundaries, the 32-detail cap, which duplicate
  wins, diagnostic redaction, and which replacement texts are fixed and which may be localized.
- **Reader reasons in check order.** The strict reader's 30 rejection reasons, the order in which it checks a frame,
  and so which reason wins when a frame breaks several rules. The manifest lists them, with two more limits (64
  diagnostic path segments, 2,048 help URI characters) and the sample payload contracts. The semantic and wire corpora
  grow from 31 and 20 cases to 77 and 34. They add single-cause cases, two-violation precedence cases, depth and
  failure-data boundaries, and an explicit client context on every case.

## The rest of the grammar, specified (D080, R7 G13)

`specs/command-line/grammar.md` now covers what only the .NET parser defined. Parsing is unchanged.

- **Parse order.** Output selection is checked over the whole command line first. The specification also gives where
  an unknown command is reported (index 0, also after leading options), and how the checks after the last token are
  ordered.
- **One error diagnostic** per parse, and the order of options in a result.
- **Help.** The `help` word, `unexpected-root-help-argument` (`RCLI1013`), and help for an invoked group.
- **Catalog features.** Required options (`RCLI1012`), environment fallbacks with their Boolean words (`RCLI1014`),
  choices and their case matching (`RCLI1015`), global options, and the negative-number token grammar.
- **Diagnostics.** The arguments of every kind, the suggestion algorithm, the message keys, and the UTF-16 limits for
  echoed tokens and short options.
- **Neutral names.** Neutral terms replace .NET names in the normative text. `RUNIC_COMMANDLINE_DEBUG=1` is the
  cross-language developer opt-in. The codes `RCLI2001`, `RCLI3000` and `RCLI3001` in the examples are marked
  illustrative.

The fixture catalog gains a global option, a `deploy` command with these option features, and a help-only group.
The grammar corpus grows from 50 to 103 cases and the output-classification corpus from 26 to 31. The Windows slash
dialect still has no corpus.
