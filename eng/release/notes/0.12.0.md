# Runic Command Line 0.12.0

Command Line 0.12.0 is the first release of the 0.18 release train (Command
Line 0.12.0, then Runic Translations 0.10.0, then Runic SDK 0.18.0). It replaces
the `1.0.0-rc.1` that `main` named after 0.11.0: release candidates take fixes
only, and this release adds features. It adds the Windows slash dialect
(#87), an exit code per outcome (#88), `--json` output for every outcome (#89),
the framework text catalog in `Runic.CommandLine`, and a key for every
user-facing framework text. The API changes are additive; package validation
against 0.11.0 is clean. Some behaviour and wording change; they are listed
under [Upgrading from 0.11](#upgrading-from-011).

## Upgrading from 0.11

Nothing is removed, and an application that declares none of the new options
parses, exits and writes JSON exactly as before. These changes can still need
action:

| Change | Who is affected | What to do |
| --- | --- | --- |
| German usage errors use the new wording, for example `Die Option '--x' ist unbekannt.` | Tests that compare German usage errors | Update the expected text. |
| `RCLI6008` and `RCLI6011` have one English message each; `ProcessResult.EnsureCompleted` reports `RCLI6006` with "The process lifecycle could not be observed safely."; `LocalExecutablePolicy` rejections carry the policy message | Tests that compare those English messages | Compare the codes and details (`argumentIndex`, `stream`, `reason`), or the new text. |
| An empty command line (no default command) has the `messageKey` `diagnostics.missing-command` instead of `diagnostics.unknown-command` | JSON consumers and tests that read the `messageKey`; resolvers and overrides that translate the argument-less `diagnostics.unknown-command` | Expect the new key; move the translation to `diagnostics.missing-command`. Kind (`unknown-command`) and code (`RCLI1002`) are unchanged. |
| `SpectreCommandConsole` writes no ANSI escapes for redirected output or `color: false` on CI hosts (GitHub Actions, Azure Pipelines and others) | Tests on CI that stripped or expected ANSI escapes | Compare the plain text. |
| A success envelope may carry an informational nonzero `exitCode` (for example 3010) | Readers of `runic.commandline/1`; readers before 0.12 reject such a frame | Update readers to 0.12, or treat `success` as the outcome and `exitCode` as the process code. Only an application that calls `WithExitCode` on a success produces it. |
| `diagnostics.invalid-choice-hidden` takes a second argument, `help` (`--help`, or `/?` under the slash dialect); JSON `arguments` are `["--token", "--help"]` | Translations of the key; tests that compare the JSON `arguments` | Use `{help}` (or `{1}`) in the translation; a translation that ignores it keeps saying `--help`. Expect the extra argument. |

German text for this release needs `Runic.Translations.CommandLine` 0.10.0.
Each Command Line minor has one adapter release line, released right after it in
the same train:

| Runic.CommandLine | Runic.Translations.CommandLine |
| --- | --- |
| 0.12.x | 0.10.x (Runic.CommandLine `[0.12.0, 0.13.0-0.0)`) |
| 0.10.x, 0.11.x | none; 0.9.1 does not accept them (`NU1608`) |
| 0.9.x | 0.9.1 (`[0.9.1, 0.10.0)`); 0.8.0 (`[0.9.0, 0.10.0)`) |

A mismatched pair fails restore with `NU1608` or shows English for newer keys.
Before publication, the release train's compatibility gate (row T, run by the
publish workflow) restores and runs this release's packages with the
Translations and Runic SDK candidates, with warnings as errors.

## Windows slash dialect and case-insensitive matching (#87)

- A catalog declares its grammar, and every runner (`CommandApp.Run` and
  `RunAsync`, `CommandLineHostingAdapter`, `PortableCommandSyntaxAdapter`,
  `CommandTestInvocation.Parse`, `CommandAppTester`), help, usage hints and
  "Did you mean" suggestions follow it:

  ```csharp
  GeneratedCommandCatalog.Create(builder => builder
      .Syntax(CommandSyntaxDialect.WindowsSlash)
      .CaseInsensitive()
      .JsonOutputAlias("/json", JsonOutputShape.Payload)
      .HelpOrder(CommandHelpOrder.Declaration));
  ```

- **`Syntax(CommandSyntaxDialect.WindowsSlash)`:** `/word` or `word` where a
  command belongs names that command; `/?` and `/help` show help and
  `/version` the version; `/name`, `/name value` and `/name=value` give
  options, whether declared as `--name`, `-n` or `/name`; `/format`, the
  selector's hidden aliases, the JSON alias and the completion option accept
  `/name` too. Unknown `/…` tokens are data, and `--` ends options. The
  portable spellings keep working. The rules for ambiguous tokens are in
  [the grammar](../../../specs/command-line/grammar.md#windows-slash-dialect).
- **`CaseInsensitive()`** matches commands, aliases, display spellings and
  options ordinally ignoring case. Values never change.
- **Display spellings:** `[Command("policy reset-all", Spelling = "resetAll")]`
  or `CommandBuilder.Spelling("resetAll")`. Help and suggestions show the
  spelling and the command line accepts it; the canonical name stays the
  identity in `ParsedInvocation.Path`, JSON and diagnostics.
- **Help order:** `HelpOrder(CommandHelpOrder.Declaration)` lists commands in
  source order (the generator emits `CommandCatalogBuilder.DeclarationOrder`).
  It affects help only; `Commands`, completion and JSON keep registration order.
- **`CommandApp.SyntaxAdapter`**, the extension point the hosting adapter
  already had.
- Help and diagnostics use the dialect's spelling: `Usage: tool /policy /link
  <name> <path> [options]`, `Run "tool /policy /link /?" for more
  information.`, `The /R option requires a value.`, `Did you mean '/policy'?`.
  `CommandLineHostingAdapter.Classify` and completion requests read the dialect.
  Completion covers the portable grammar, which the dialect also accepts, and
  now offers display spellings.
- Catalog validation: `RCLI0002`, `RCLI0004`, `RCLI0007`, `RCLI0008`,
  `RCLI0018` and `RCLI0024` cover display spellings, collisions that only the
  dialect or case-insensitivity create, and slash JSON aliases. New `RCLI0027`
  rejects `CommandCatalog.Combine` of catalogs with different syntax, case
  sensitivity or help order.
- **Behaviour change:** `diagnostics.invalid-choice-hidden` has the arguments
  `parameter, help` (English: `{parameter} must be one of the choices shown in
  {help}.`), and the argument-less `invalid-choice` fallback no longer names
  `--help`. Under the slash dialect an unknown-option suggestion of `-h` is
  written `/?`.

A catalog that declares neither the dialect nor case-insensitivity parses
exactly as before.

## An exit code per outcome (#88)

- `CommandOutcome<T>.WithExitCode(int)` returns a copy that exits with the
  given code, for example
  `CommandOutcome.Failure<T>(CommandExitCategory.Unavailable, fault).WithExitCode(3)`.
  `CommandOutcome<T>.ExitCode` (`int?`) exposes it; null means the exit-code
  policy decides. Usage errors, binding and validation failures, cancellation
  and host failures keep the policy's codes, and policies are unchanged.
- A failure refuses `0` and any multiple of 256, which Linux and macOS
  truncate to 0 (`ArgumentOutOfRangeException`).
- **Informational success codes:** `CommandOutcome.Success(x).WithExitCode(3010)`
  stays a success for `Succeeded` and observers. Linux and macOS report only
  the low 8 bits (3010 reads as 194), and a caller that does not know the code
  reads it as a failure.
- Every channel reports the returned code: the envelope's `exitCode`,
  `CommandExecutionResult.ExitCode`, `HostedCommandLineExecutionResult.ExitCode`,
  `CommandOutcomePresentation<T>.ExitCode` and the `Completed` observer event.
- **Protocol:** `runic.commandline/1` allows `success: true` with a nonzero
  informational `exitCode` (`specs/command-line/protocol/examples/informational-success.json`).
  The reader in this release accepts it; readers before 0.12 reject it.
- **Help:** `[CommandExitCode(code, "description", DescriptionKey = …)]`, or
  `CommandHelp.ExitCodes` with `CommandExitCodeHelp` for hand-registered
  commands, adds an "Exit codes:" section after Options. New key
  `help.exit-codes` ("Exit codes"); `ValidateDescriptionKeys` checks the
  description keys.

## `--json` for every outcome (#89)

New `CommandApp.JsonOutput` (`CommandJsonOutputOptions`), which also flows to
`CommandPresentation.JsonOutput`, `CommandOutputDispatcher.JsonOutput`, the
hosting adapter and `CommandAppTester`. The options are independent and off by
default; without them, output is byte for byte that of 0.11.0.

| Option | Default | Effect |
| --- | --- | --- |
| `DocumentEveryOutcome` | false | The payload shape (`JsonOutputShape.Payload`) writes a document for every outcome. Usage errors, including parser errors on `--json` command lines, binding and validation failures, domain failures without failure data, cancellation and host failures write the standard envelope with fault code, message, diagnostics and exit code. Help and version write a JSON string; a `CommandUnit` command writes `{}`. Declared failure data stays the bare document. |
| `QuietStandardError` | false | JSON mode writes nothing to standard error: no framework diagnostics, fault line, usage hint or RCLI5000 hint, and also none of the text the handler writes to its console, which JSON mode moves to standard error. `RUNIC_COMMANDLINE_DEBUG` output is still written. |
| `Escaping` | `Unicode` | `Ascii` writes every non-ASCII character as `\uXXXX` in envelopes, payloads and failure data, for consoles that do not decode UTF-8 (Windows PowerShell 5.1, OEM code pages). |

The envelope mode (`--format json`, `RUNIC_COMMANDLINE_OUTPUT=json`, an
envelope alias) already wrote one envelope for every outcome; tests now pin it.

## Framework text catalog in Runic.CommandLine

- The English and German framework text (the `runic-command-line` catalog)
  moved from `Runic.Translations.CommandLine` into this repository, next to
  `CommandTextKeys`. The `Runic.CommandLine` package carries it as data under
  `translations/` (`runic.json`, `en.rmf2`, `de.rmf2`) with
  `translations/text-keys.json`, which lists every key with its argument names
  and catalog message name. Nothing there flows into a consuming project, and
  Runic.CommandLine still does not reference Runic Translations.
- The catalog covers every key, including `hints.usage` (German: `Weitere
  Informationen erhalten Sie mit "{command}".`), and its English is the
  English that 0.10 and 0.11 write for usage errors.
- `Runic.Translations.CommandLine` follows each Command Line minor in lockstep;
  the Runic.CommandLine README has the version table. German text for this
  release needs `Runic.Translations.CommandLine` 0.10.0.

What to do: nothing in code. An application that overrides framework text in
`translations/overrides/runic-command-line/` keeps working; the German wording
of the usage errors changed with the English (for example `Die Option '--x'
ist unbekannt.`), so tests that compare German usage errors need the new text.

## Every framework text has a key

- **Process faults.** `RCLI6001` to `RCLI6011` of `Runic.CommandLine.Processes`
  are translated through `faults.{code}` like the other framework faults. The
  keys are part of `CommandTextKeys.All`, the new `ProcessTextKeys` in
  Runic.CommandLine.Processes names them, and their English and German text is
  in the same `runic-command-line` catalog, so `Runic.Translations.CommandLine`
  translates them without a reference to Runic.CommandLine.Processes.
- **One English message per process fault code.** A translation replaces a
  fault message by code, so codes with two messages now have one:
  `RCLI6008` says "The batch file path or an argument contains characters that
  cmd.exe would interpret.", `RCLI6011` says "The captured output is
  incomplete: it exceeded its capture limit, or a descendant process held the
  output pipe open.", and `ProcessResult.EnsureCompleted` reports `RCLI6006`
  with the runner's "The process lifecycle could not be observed safely.".
  `LocalExecutablePolicy` rejections carry the runner's policy message. The
  details (`argumentIndex`, `stream`, `reason`) still tell the cases apart.
- **Empty command line.** Without a command (and without a default command),
  the `unknown-command` diagnostic (`RCLI1002`) now has the key
  `diagnostics.missing-command`, "No command was given.", instead of
  `diagnostics.unknown-command` without its argument. Its kind and code are
  unchanged; its JSON `messageKey` changes.
- **Help links and redaction notes.** The `Help for {code}: {link}` line has the
  key `hints.help-link`, and the notes that replace redacted messages have
  `redaction.diagnostic-content`, `redaction.diagnostic-message` and
  `redaction.fault`. The notes are translated in human and JSON output. The
  `[redacted]` marker in fault details stays as it is.
- **Spectre help headings.** `SpectreHelpPresenter` styles the usage line and
  section headings by their resolved labels, so `Aufruf:` and the other German
  headings are styled. A description line that happens to end with a colon is
  no longer styled as a heading.
- **Spectre colour in CI.** `SpectreCommandConsole` no longer lets Spectre's
  CI detection (GitHub Actions, Azure Pipelines and others) turn ANSI back on:
  redirected output and `color: false` are plain text on CI hosts too.

What to do: a resolver or override that translates `diagnostics.unknown-command`
for the empty command line moves that text to `diagnostics.missing-command`.
Tests that compare the English `RCLI6008`, `RCLI6011` or `LocalExecutablePolicy`
messages, or the `messageKey` of an empty command line, need the new values.
