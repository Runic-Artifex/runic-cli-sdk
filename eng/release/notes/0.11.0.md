# Runic Command Line 0.11.0

The next release after 0.10.0 is 0.11.0, not `1.0.0-rc.1`: it takes
the gaps that the Runic consumer applications found. It adds API and changes
human output only; nothing is removed.

## Human output keeps the line breaks of a message

- **Behaviour change:** the default human writer (`CommandApp`,
  `CommandLineHostingAdapter`, `CommandOutputDispatcher` and
  `CommandOutcomePresentation<T>.WriteDefaultAsync`) keeps the line breaks of a
  fault or diagnostic message. `\n` and `\r\n` are written as `\n`, leading
  and trailing line breaks are dropped, and a line does not end in a space.
  Before, every line break became a space, so a message such as
  `2 problems in saltmarch:\n  codex/a.md: bad` was one long line, and an
  application that wrote messages on several lines needed its own presenter.
  Other control characters still become a space, a message with technical
  content on any line is still redacted as a whole, and a translation of the
  fault (`faults.{code}`) keeps its own line breaks.
- JSON output, `CommandResponse<T>.Fault` and the strict envelope readers are
  unchanged: protocol messages stay on one line.

What to do: tests that compare human standard error with the flattened text of
a multi-line message need the line breaks. An application that kept a presenter
only to write such messages unchanged can remove it.

## `--output json` suggests the output selector

- `--output` selected the output before 0.8.0, and old scripts that still pass
  it failed with `The option '--output' is not recognized.` Where `--output`
  is not a spelling of the catalog, `--output human` or `--output json` (also
  `--output=json`, and before the command) is still the usage error
  `RCLI1001` `unknown-option` (`RCLI1002` `unknown-command` before the
  command), but its message suggests the selector:
  `The option '--output' is not recognized. Did you mean '--format'?`. The
  diagnostic uses the existing suggestion key
  (`diagnostics.unknown-option-suggestion`, the selector as its last argument).
  `--output` with any other value suggests nothing, as it names an option the
  command lacks.
- Command Line does not accept `--output` by default. A default hidden alias
  would reserve the spelling in every catalog: catalog validation
  (`RCLI0026`) would then reject the commands that have their own
  `--output <file>` option, and removing the alias at 1.0 would change the
  parsing rules during the release candidates, which take fixes only. An
  application that wants to keep its old scripts working declares the alias,
  as since 0.8.0: `builder.OutputSelector("--format", "--output")`.

## The output selector's spelling on the assembly

- New `[assembly: OutputSelector(name, params hiddenAliases)]`
  (`OutputSelectorAttribute`): the generated catalog declares that selector,
  so an application whose commands have their own `--format`, such as
  `storyline bind --format epub`, keeps it and moves the selector to, for
  example, `--output-format`. `GeneratedCommandCatalog.Create(configure)`
  declares it before `configure` runs, which may still declare another.
  `CommandCatalogBuilder.OutputSelector` (since 0.8.0) is unchanged and remains
  the way for hand-written catalogs; `--format` stays the default.
- Generator warning `RCLI9045` now checks options against the declared
  selector and its aliases, so it no longer fires for `--format` once the
  assembly declares another selector. Its message names the attribute, and its
  title is now "Option spelled like the output selector".
- New generator error `RCLI9046` `Invalid output selector`: a spelling of the
  attribute that `CommandCatalogBuilder.OutputSelector` would reject (not a
  long option spelling, `--help` or `--version`, or given twice). The
  generated catalog then declares no selector.

## Exit categories: input-shaped errors exit 2, domain failures exit 1

- `CommandExitCategory.Validation` is for input a handler rejects because of
  its shape, whatever the state the command works on (two options that
  exclude each other, `--since` later than `--until`), and exits 2 like
  `Usage`. A domain failure on well-formed input (a business rule refused the
  operation, a check found problems, a conflict) is `CommandFailure`, and a
  missing or unreachable resource `Unavailable`; both exit 1. The XML
  documentation of `CommandExitCategory` and `CommandExitCodes`, the exit code
  table of the `Runic.CommandLine` README and the protocol README state this
  mapping; before, they gave "a business rule" as an example of `Validation`.
  The categories and exit codes are unchanged.

What to do: a handler that returns `Validation` for a domain failure should
return `CommandFailure`, so that scripts can tell "fix the command line" (2)
from "the operation failed" (1).

## Command Line Processes

- New `ProcessRunnerExtensions.RunAsync(this IProcessRunner runner, ProcessRequest request, CancellationToken cancellationToken)`:
  `runner.RunAsync(request, token)` runs the request without an output
  handler. Before, the token was taken for the output handler and the call
  failed with CS1503; a named `cancellationToken:` argument keeps working.
- New `ProcessOutput.Bytes`: the retained bytes of a channel exactly as the
  child wrote them, with the same retained-byte cap, for output that is not
  text in one encoding, such as the file names Git writes. `ProcessOutput.Text`
  is now decoded when it is first read. A capture created with
  `new ProcessOutput(text)` has the text's UTF-8 as its bytes.
- New `ProcessOutput.FromBytes(bytes, encoding = null, observedByteCount = null, isTruncated = false, drainTimedOut = false)`
  creates a capture of raw bytes for a test double; its `Text` decodes them
  with the encoding, UTF-8 by default.

What to do: a caller that decodes `Text` back to bytes with a single-byte
encoding (`Encoding.Latin1` for the channel, then `Encoding.Latin1.GetBytes`)
can read `Bytes` instead and keep the default encoding.
